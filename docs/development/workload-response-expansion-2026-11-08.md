# 워크로드 대응 확장 · 실행 기록

기준: Sova `1a63ecf23e5c7b5d70aebedb31763b36a376534a`, security `4d93137416ef947e9fc3924403c7a9580f50455c`.
기존 성공은 단일 무상태 API의 전용 온프렘 시험이다. 아래 확장 완료로 소급하지 않는다.

## 필수 작업과 인수 기준

- [x] 발신 차단 실측: 동일 actor Pod→동일 neighbor Pod의 새 직접 TCP/HTTP 연결이 전에는 성공하고 정책 적용 후 거부되는지 확인한다. DNS 실패와 섞지 않으며 이웃의 독립 정상 응답을 함께 확인한다.
- [x] 기존 연결 종료: 정책만으로 종료됐다고 가정하지 않는다. 승인한 원본 Pod fencing과 기존 클라이언트 소켓 닫기·읽기 루프 종료를 함께 검증했다.
- [x] 부분 격리 확대: API·무상태 작업자·이웃을 등록하고 API 단독 및 API+작업자 선택 집합의 실제 격리를 확인했다. 공유 DB·큐는 포함하지 않았다.
- [x] 실패·재검증: 실제 대체 API 검증 실패 시 경로 유지를 확인했다. 별도 계획·승인 후 새 근거로 재검증했다.
- [x] 복귀: 별도 승인·현재 artifact 재검증 후 새 원본 Pod와 원본 경로 복귀를 확인했다. 사고 보류는 유지했다.
- [ ] 일반 탐지 연결: 기존 T33 Falco/Kyverno 계약·수집기를 재사용한다. 고정403을 일반 공격 탐지로 표현하지 않는다. detector 설치·실제 이벤트 수집·중단/만료·자원 매핑을 검증한다.
- [ ] 고객 앱·운영 T10 연결: 기존 T7/T9·T10·T19·T31/T12의 정본 권한·승인·실행·복구 경로를 사용한다. 실제 계획·본인 읽기 권한과 공유 실행 구간이 없으면 보류한다.
- [x] 콘솔: 위 전용 시험 범위의 현재 관측·과거 영수증·검증 실패·승인·복귀를 기존 Sova 지도에 연결했다. 운영 T10 콘솔 인수와 구분한다.
- [x] 공유용 시연: API 단독과 API+작업자를 실제 실행·정리했다. 각 실행의 원본·실패·화면·정리 증거와 운영 미완료 항목을 보존한다.

## 변경 원칙

기존 가드·불변 계획·효과 원장을 재사용한다. 새 탐지 엔진과 실행 엔진은 만들지 않는다.
실환경 시험은 새 소유 namespace에서 먼저 수행하며 기존 공유 앱·DB·Edge는 변경하지 않는다.
공유 노드의 privileged detector 설치, 운영 신원 부여, 다른 담당의 핵심 코드 변경은 담당자 합의를 선행한다.
문서 SHA, 코드 생산자 SHA, 실제 이미지 digest와 실행 시각은 구분해 기록한다.

## 조사

- 기존 격리 정책은 ingress/egress를 모두 선언하지만 기존 증거는 독립 Pod→원본 새 연결에 한정한다.
- Kubernetes 공식 문서는 기존 연결에 대한 NetworkPolicy 변경 효과가 구현체에 따라 달라진다고 명시한다. 따라서 기존 연결 종료는 별도 검증한다.
  - https://kubernetes.io/docs/concepts/services-networking/network-policies/
- 실제 Falco modern eBPF 설치에는 노드 수준 권한과 클러스터 자원 배정이 필요하다. 기존 배치를 먼저 조회한다.
  - https://falco.org/docs/setup/container/
- 운영 인계는 기존 제품의 계획·권한·실행 경로를 사용한다. 개인 시험 권한을 운영 승인으로 대신하지 않는다.

## 발신 차단 실제 인수

- 실행 생산자: `8d08852630efa7e4219f329b3276e2a69a42ed58`.
- 로컬 회귀 64개 통과. 별도 온프렘 실행에서 source→peer 정상 대조 뒤 같은 Pod IP에 대한 새 TCP 연결 2회 거부를 확인했다.
- peer의 현재 Pod UID/IP와 ReplicaSet→Deployment 소유권을 전후 대조했다. DNS 실패·peer 장애를 차단 증거로 사용하지 않았다.
- 원본 수신 차단·이웃 정상·Green 기동·실제 시험 경로 전환과 화면 8단계·발신 차단 선 표시를 확인했다.
- 모바일 넘침·브라우저 오류 없음. 세션 회수 시 화면 자료 철회·소유 namespace 전부 부재 확인.
- 기존 연결 종료와 복수 구성 요소, 일반 탐지·운영 T10 인수의 완료 근거로 확대하지 않는다.
- 원본 baseline·두 방향 측정·효과 영수증·화면·정리는 비공개 `response-expansion-20261108` 기록에 보존한다.
- 고정403 자격 시험과 일반 런타임 탐지의 자격 시험은 별개로 관리한다.

## 부분 격리·실패 보류·복귀의 실제 인수

- 그룹 생산자: `16d4bb9` 전체 SHA는 공개 인수 요약에 고정한다. API와 작업자를 모두 격리하고 실제 새 수신·발신 거부, 원본 Pod 제거, 기존 스트림 읽기 종료, 이웃 정상 응답을 확인했다.
- 단독 생산자: `89fa11c`. API만 격리했으며, 작업자 Pod UID와 실제 응답은 모든 변경 readback에서 유지됐다. 이웃도 계속 정상 응답했다.
- 두 실행 모두 실제 검증 실패 → 원본 경로 유지 → 새 계획 승인 → Green 전환 → 별도 복귀 계획 승인 → 새 원본 Pod·실행 imageID·불변 ConfigMap 검증 → 원본 경로 복귀를 통과했다.
- 사건 보류는 복귀 후에도 남았다. 모바일 넘침·브라우저 오류가 없고, 브라우저 세션 회수 후 지도 자료가 철회됐다. 소유 namespace 세 개 모두 부재를 확인했다.
- 실행 시점의 승인 범위·이미지·기한을 화면에 표시하고, 계획이 바뀌면 동의 체크를 해제했다. 현재 UI·전체 단계도 단독 실제 실행에서 확인했다.
- 집중 회귀 74개와 기존 효과 원장 회귀를 합한 86개 통과. 이 수치는 프로토콜·루프백 회귀이며 실제 클러스터 두 실행과 별개다.

### 실패와 수정 기록

1. 준비 기준선이 끝나기 전에 등록 자료만으로 READY가 표시되는 경합을 실제 시험에서 발견했다. 기존 연결 기준선 수집 완료 후에만 READY가 되도록 수정하고 회귀를 추가했다.
2. Kubernetes GET 응답에서 빈 ingress/egress 배열이 생략돼 동일한 deny 정책도 불일치로 처리됐다. 빈 규칙 생략만 정규화하며 허용 규칙·넓어진 selector는 계속 거부한다.
3. 읽기 전용 검증 실패를 불확실한 외부 변경으로 기록해 원장이 재검증을 잠갔다. 기존 원장의 잠금은 올바른 동작이었다. 순수 검증을 기존 `EvidenceRecord`로 분리하고, 변경의 UNKNOWN 잠금·재실행 금지는 유지했다. 실패 검증을 덮어쓰지 않는 회귀를 추가했다.
4. 브라우저 시험 하네스의 재승인 체크 누락과 이전 세션 종료 상태 경합은 제품 성공으로 처리하지 않았다. 각 실패를 보존하고 하네스를 수정했다. 최종 두 실행의 성공 결과와 섞지 않는다.

### 제품 운영 경로 인수

일반 런타임 탐지·실제 고객 앱·운영 계획 및 승인 경로는 전용 fixture의 성공과 분리해 인수한다. 운영 환경 조회 결과·계획 참조·접속 권한 상태는 비공개 기록에 보존한다. 공용 자원 변경과 보안 설정 공개는 해당 담당자의 인수 범위를 따른다.

연결할 기존 도구와 경계·인수 기준은 [지원 범위 문서](../workload-response-acceptance.md)에 정리했다.
