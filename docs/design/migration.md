# 앱·데이터 이전과 복구

상태: 프로덕션 목표 상세 계약. 읽기 전용 검사와 통제된 앱 전환을 구현·시험했으며 일반 운영 worker의 DB 이전 연결은 남아 있다.

## 1. 이전 프로필

| 프로필 | 계약 |
| --- | --- |
| bounded_write_pause | 계획에서 승인한 시간 동안 쓰기를 제한한다. 읽기·기존 연결 정책과 제한 초과 시 동작을 명시한다. |
| continuous_service | 지정 부하와 관측 창에서 사용자 기준의 오류·지연·쓰기·세션 SLO를 충족한 경로에만 부여한다. |

DB 이전과 앱 이전을 별도 워크플로로 만들되 하나의 계획 DAG·revision·복구 계약으로 조정한다. 앱을 먼저 전환하고 DB를 나중에 바꿀 수도 있지만 중간 구성의 지연·보안·위치 정책을 만족해야 한다. 블루그린이나 Kubernetes rollout만으로 DB 무중단을 보장하지 않는다.

## 2. 사전 조사·준비

- 모든 writer: API, worker, cron, 관리자, 배치·직접 SQL과 연결 풀을 조사한다.
- PostgreSQL 버전·확장·인코딩·collation·DDL·대용량 객체·시퀀스·권한·복제 가능성을 확인한다.
- 원본·대상·backup 위치, TLS·키·Secret·접근 경계·목적지 HA를 검증한다.
- 출발과 목적지의 실제 연결 권한을 분리한다. Sova 제어 DB는 앱 데이터 경로에 포함하지 않는다.
- 검증용 복사로 무결성·업무 쿼리·용량·복구 시간을 측정한다. 운영 원문은 허가 없이 샌드박스로 복사하지 않는다.
- 초기 복사와 변경분 동기화를 시작한다. 지연·WAL 보존·디스크 증가·장애 시간을 관측하고 중단 한도를 둔다.

## 3. 전환 절차

1. 정확한 계획·정책·원본/대상 revision·승인·비용·기한·보안 보류를 실행 직전에 다시 조회한다.
2. 새 쓰기 수용을 제어하고 진행 중 트랜잭션을 drain한다. 제한 시간이 지나면 강제 종료 허용 여부에 따라 중단한다.
3. 모든 기존 writer를 실제 DB/신원 경계에서 fence한다. 역할 폐기·세션 정리·관리 접근 예외까지 검증한다.
4. 같은 복제 경로에 barrier를 기록하고 대상의 실제 반영을 읽어 확인한다. 다른 구독의 LSN이나 단순 지연 0은 동등 증거가 아니다.
5. 테이블·PK·정규화한 행 내용·범위별 hash·건수를 비교한다. 시퀀스·권한·확장·DDL은 별도로 확인한다. logical replication이 자동 복제하지 않는 상태를 보충한다.
6. 대상 writer를 새 epoch로 활성화하고 원본의 일반 쓰기가 계속 차단되는지 확인한다.
7. 새 앱이 대상 DB를 사용하도록 설정한 뒤 안정 진입점의 경로를 전환한다. 실제 경로 readback과 인증된 신규 읽기·쓰기를 검증한다.
8. 지연·실패·업무 중복·데이터 결과를 관측한다. 검증 실패는 성공 처리하지 않는다.

리스 epoch는 Sova 워커의 실행권이다. DB와 외부 자원이 이를 적용하지 않으면 실제 fencing이 아니다. 외부 효과 응답 유실은 조회 전용 복구로 처리한다.

## 4. 신규 쓰기 이후 복구

대상에 쓰기가 없을 때와 이미 쓰기가 생긴 때를 구분한다. 신규 쓰기가 있으면 대상을 먼저 fence하고, 승인한 역방향 동기화·최종 barrier·무결성·시퀀스·원본 writer 복원을 수행한다. 이 경로가 준비되지 않았으면 데이터 손실을 동반하는 자동 복귀를 실행하지 않고 양쪽 쓰기를 차단한 상태로 운영자에게 인계한다.

원본 보존 기간과 복제 제거·Secret 폐기·backup·과금 자원 삭제는 별도 정리 단계다. 앱 전환 완료가 출발 자원 정리 완료는 아니다.

## 5. 쓰기 대기·세션

PgBouncer의 pause/resume과 안정 DB 접속점은 후보로 검증한다. 열린 트랜잭션·세션 기능·prepared statement·타임아웃·접속 재시도·고가용성·목적지 재지정 절차를 시험하기 전에는 오류 없는 대기를 보장하지 않는다. 재시도는 idempotency key와 업무 중복 방지가 필요하다. 대기 큐도 유한해야 하며 초과 동작을 계약에 둔다.

WebSocket·메모리 상태·장기 세션은 별도 프로필이다. 재접속·세션 외부화·업무 복구 기준을 정의하기 전에는 HTTP 경로 전환 결과를 게임 세션 무중단으로 표현하지 않는다.

## 6. 운영 수용 기준

승인한 부하에서 p95/p99 지연, 실패·timeout·중복·미완료 쓰기, 전환 창, 실제 신규 데이터, 원본 쓰기 거부와 목표 RPO/RTO를 측정한다. 각 경계의 프로세스 종료·응답 유실·큐 중복·복제 중단·부분 경로 전환·인증 폐기·복구 중 재장애를 주입한다. 원본·대상 양쪽에 동시 일반 writer가 허용된 순간이 있으면 자격 실패다.

## 2026-11-02 구현 경계

등록한 cluster/database/table OID·schema digest·reader를 확인하는 읽기 전용 snapshot과 sequence 관측을 추가했다. 네트워크 DB는 `verify-full` TLS를 요구하며 Unix socket 예외는 명시적 사설 시험 등록에 한정한다. NOINHERIT 회원 역할의 쓰기 권한도 reader에서 거부한다.

publication의 전체 테이블·열·변경 종류·row filter, subscription identity·초기 동기화 상태·정확한 barrier를 검사한다. 목적지 앱 DB의 별도 migration owner가 설치하는 고정 `channel_state()`는 구독 비밀번호 대신 승인된 연결 설정의 digest만 노출한다. observer의 role OID·구독 OID·만료·함수 소유자/정의에 결합한다. 설치 SQL은 제어 DB migration이 아니며 앱 이미지에 포함하지 않는다.

실제 논리 복제와 통제된 상담앱의 DB 전환을 시험했다. 7개 데이터 테이블·별도 파일 bytes·시퀀스 보정·목적지 신규 쓰기·중복 방지를 확인했다. 앱의 advisory drain은 하나의 실제 DB transaction 안에서 수행한다. 단, 연결 설정 digest의 일치는 구독 연결의 실시간 TLS 신원·모든 writer 봉쇄·역방향 복구를 대신하지 않는다. 이 구성 요소의 성공 응답은 `cutover_authorized=false`다.

Snapshot 정규화는 `postgres-lossless-v2`로 구분한다. NUMERIC은 decimal context 반올림 없이 처리하고 JSON/JSONB의 큰 소수·타입·SQL NULL과 JSON null을 보존한다. 중복 JSON key·지원 한도 초과를 차단한다. 서로 다른 정규화 버전의 manifest를 비교하지 않는다. DB 측 textual row cap과 statement timeout을 적용하지만 source CPU·격리·실부하 자격은 별도다.
